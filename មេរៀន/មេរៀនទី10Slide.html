The Stateless Challenge: Why Web Applications Need Server-Side Sessions

សាកលវិទ្យាល័យអង្គរ ANGKOR UNIVERSITY
🎯 គោលគំនិត ៖ HTTP Protocol គឺជាប្រព័ន្ធ Stateless មានន័យថា Server មិនចងចាំសំណើដែលធ្លាប់កើតឡើងពីមុនឡើយ។ រាល់ Request ថ្មី Server ចាត់ទុកជាមនុស្សប្លែកមុខជានិច្ច!

C1 បញ្ហាប្រឈមនៃ Stateless HTTP

  • No Memory ៖ បើគ្មាន Session ទេ ពេល User Login លើ login.php រួចចុចចូល dashboard.php Server នឹងភ្លេចអត្តសញ្ញាណភ្លាម។
  • User Experience ៖ បើគ្មាន State Management ទេ User ត្រូវបង្ខំចិត្តវាយ Password គ្រប់ទំព័រដែលខ្លួនចុច!
  • ដំណោះស្រាយ ៖ ប្រើប្រាស់ Sessions (Server-side) និង Cookies (Client-side)។

យន្តការ PHPSESSID Token

នៅពេល session_start() ត្រូវបានហៅ ៖

  • PHP បង្កើតលេខកូដចៃដន្យ Session ID (ឧ. PHPSESSID=4d9f1e...) ផ្ញើទៅ Browser ជា Cookie។
  • ទិន្នន័យជាក់ស្តែង (User ID, Role) ផ្ទុកក្នុង Server Storage។
  • Browser ភ្ជាប់តែ Session ID មក Server រាល់ពេលបើកទំព័រថ្មី ដើម្បីបើកទូទិន្នន័យដែលត្រូវគ្នា។

The Complete Session Cycle: Initialization, State Mutation, Inspection & Persistence

សាកលវិទ្យាល័យអង្គរ ANGKOR UNIVERSITY

C3 ជំហានទាំង ៣ នៃ Session Workflow

// 1. ចាប់ផ្តើម Session if (session_status() === PHP_SESSION_NONE) { session_start(); } // 2. កំណត់ទិន្នន័យ Session (Write State) $_SESSION['user_id'] = 101; $_SESSION['username'] = "soeurng_lim"; $_SESSION['role'] = "Admin"; // 3. អានទិន្នន័យ Session (Read State) echo "ស្វាគមន៍៖ " . $_SESSION['username'];

របៀបដែល PHP គ្រប់គ្រង Session

  • Auto File Creation ៖ PHP បង្កើតឯកសារសម្ងាត់ sess_4d9f1e8a9c... ក្នុង Server Directory (ដូចជា xampp/tmp)។
  • Data Persistence ៖ រាល់ពេល User ចុច Refresh ឬប្តូរទំព័រ $_SESSION នៅតែរក្សាតម្លៃដដែលរហូតដល់ Browser បិទ ឬ User ចុច Logout។
  • Type Flexibility ៖ $_SESSION អាចផ្ទុកបានទាំង String, Integer, Array និង Object!

១០.២.២ ការបញ្ចប់ Session ពេល Logout (4-Step Destruction)

Complete Session Teardown: Clearing Memory, Invalidating Cookies, and Destroying Storage

សាកលវិទ្យាល័យអង្គរ ANGKOR UNIVERSITY

C3 ជំហានទាំង ៤ នៃ Secure Logout

  • ជំហានទី ១ (Memory Wipe) ៖ $_SESSION = []; (សម្អាតរាល់អថេរក្នុង RAM)។
  • ជំហានទី ២ (Cookie Expire) ៖ setcookie(session_name(), '', time() - 42000, '/'); (បញ្ជា Browser ឱ្យលុប PHPSESSID ចោល)។
  • ជំហានទី ៣ (Server File Purge) ៖ session_destroy(); (បំផ្លាញឯកសារ Session ចេញពី Storage)។
  • ជំហានទី ៤ (Redirect) ៖ header("Location: login.php?msg=logged_out"); exit;

logout.php (Complete Script)

<?php if (session_status() === PHP_SESSION_NONE) { session_start(); } $_SESSION = []; // 1. សម្អាត memory if (ini_get("session.use_cookies")) { // 2. លុប cookie $p = session_get_cookie_params(); setcookie(session_name(), '', time() - 42000, $p["path"], $p["domain"]); } session_destroy(); // 3. បំផ្លាញ storage header("Location: login.php?msg=logged_out"); // 4. Redirect exit; ?>

The Threat of Fast Hashes: Rainbow Tables, Hash Collisions, and GPU Brute-Force Attacks

សាកលវិទ្យាល័យអង្គរ ANGKOR UNIVERSITY

ហានិភ័យនៃ Fast Hashes (MD5 / SHA-1)

  • Fast Calculation ៖ MD5 ត្រូវបានរចនាសម្រាប់ Checksum ឯកសារ ដូច្នេះវាលឿនជ្រុល។ ឧបករណ៍ GPU ទំនើបអាច Brute-force បាន រាប់ពាន់លាន Hashes ក្នុង ១ វិនាទី!
  • Rainbow Tables ៖ Hacker មានតារាង Look-up Table រួចជាស្រេច អាចស្វែងរក Password ពី MD5 ត្រឹមតែ ០.១ វិនាទី!
  • No Salt by Default ៖ Password ដូចគ្នា ផ្តល់ MD5 ដូចគ្នា ១០០%។

ឧត្តមភាពនៃ Slow Hashes (Bcrypt / Argon2)

  • Key Stretching & Cost Factor ៖ បង្ខំឱ្យ CPU ចំណាយពេលគណនា (ឧ. 2^10 ឬ 2^12 iterations) ធ្វើឱ្យ GPU គាំងពេលព្យាយាម Brute-force។
  • Automatic Cryptographic Salt ៖ បូកបន្ថែមអក្សរចៃដន្យ ធ្វើឱ្យ Rainbow Tables អស់ប្រសិទ្ធភាពទាំងស្រុង។
  • PHP 8 Standard ៖ ប្រើ PASSWORD_DEFAULT ជានិច្ច!

១២. វិធានសុវត្ថិភាពល្អបំផុត (Production Security Best Practices)

Enterprise Guidelines: HTTPS Enforcement, Cookie Flags, Rate Limiting & Re-hashing

សាកលវិទ្យាល័យអង្គរ ANGKOR UNIVERSITY

វិធានការពារបណ្តាញ និង Cookie

  • Strict HTTPS Enforcement ៖ ការពារការលួចស្ទាក់ចាប់ Plain Passwords និង Session Cookies លើ Public Wi-Fi (MitM Attacks)។
  • HttpOnly & Secure Flags ៖ កំណត់ session.cookie_httponly = 1 ក្នុង php.ini ការពារការលួច Session តាមរយៈ JavaScript XSS Attacks។

ការពារ Brute-Force & Re-hash

  • Rate Limiting ៖ កំណត់ការ Login ខុសមិនឱ្យលើសពី ៥ ដង (បើលើសត្រូវ Lock គណនី ១៥ នាទី)។
  • Automatic Re-hash ៖ ប្រើ password_needs_rehash() ពេល Login ដើម្បី Re-hash Password ស្វ័យប្រវត្តិនៅពេល Server ដំឡើងកម្រិត Cost Factor ខ្ពស់ជាងមុន!
